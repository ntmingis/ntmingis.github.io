Falco + auditd: detecting fileless execution in Docker

Question

Can a container runtime monitor see fileless attacks, meaning code that runs without a normal file on disk, and does each alert name the right technique?

Answer

Out of the box, Falco caught 4 of 11 cases directly. With my 6 custom rules: 8 of 11, but I also found 2 false-positive sources. auditd recorded every successful payload in the baseline run, as raw telemetry rather than alerts.

So what inference

In this lab, default rules left most techniques undetected, and tuning closed half the gap while adding alert noise. A detection control should be tested against both attacks and normal workloads before it is counted as a control.

E1 · detection

4 → 8 of 11

Direct detections, default → custom rules, 5 runs each. One case was blocked by Docker's noexec /dev/shm, not missed.

E4 · unseen variants

1 → 4 of 7

Written after the rules were frozen. Strict fileless subset: 0 → 2 of 5. Small sample.

E2 · false positives

2 FP sources

My inline-code rule fired on benign python3 -c; gcc/make builds triggered a default rule.

E5 · overhead

n=5 inconclusive

Differences stayed within baseline variation, so no overhead figure is claimed.

What the research shows

Findings are measured. Implications are my inferences from one lab environment, not general measurements.

  1. Finding

    Default rules directly detected 4 of the 11 cases.

    Implication

    "Installed" is not "effective". A detection tool should be tested against the techniques it is meant to cover before it is reported as a working control.

  2. Finding

    Custom rules raised coverage to 8 of 11, but my inline-code rule also fired on normal python3 -c use.

    Implication

    Coverage and alert noise trade off. Every rule change needs a false-positive test on normal workloads, the same way code needs regression tests.

  3. Finding

    Renaming the process (exec -a) or feeding code through stdin still evaded both rule sets.

    Implication

    Rules keyed on process names or arguments are brittle. Signals based on behaviour at the syscall level held up better here, which matches auditd recording every successful payload.

  4. Finding

    One case was blocked by Docker's noexec /dev/shm, not missed. auditd logged auid=minh uid=root for sudo actions.

    Implication

    Reports must separate prevented, detected and missed. Hardening settings and accountability logging are controls in their own right and should be credited as such.

Limits

  • Small samples, one VM, one kernel.
  • I wrote both the variants and the rules, so the "unseen" test is not blind.
  • The overhead result is inconclusive at n=5, not "zero overhead".

What I would do next

  • Re-run with a blind variant set written by someone else.
  • Repeat on more hosts and kernels; measure overhead with a larger sample.
  • Publish the rules with an ATT&CK coverage matrix and their FP tests.

Full method and raw results: objective → setup → tests → results → takeaways → limits

01 Objective

Fileless techniques (memfd, /dev/shm, /proc/self/fd, interpreter inline code, curl | bash, LD_PRELOAD, ptrace) run code without a normal on-disk binary. Which ones do runtime tools see, and does the alert name the right technique?

02 Setup

  • Ubuntu 22.04 VM; containers on an internal Docker network, Internet egress blocked and tested; benign payloads only.
  • Falco 0.45.0 modern eBPF: 25 default rules, then 6 custom rules; rule updates frozen and config hashes recorded per run.
  • auditd rules on memfd_create, execve/execveat, ptrace.
  • Bash harness; Python parsers for Falco JSON and audit logs.

03 Tests

  • 11 cases × 5 repetitions, each labelled direct, misattributed, missed or blocked.
  • 7 unseen variants written after the custom rules were frozen.
  • Benign workloads for FP: container lifecycle, HTTP, churn, PostgreSQL, gcc/make, Python.
  • Overhead against a no-monitoring baseline.

04 Results

  • E1: 4/11 direct with default rules, 8/11 with custom rules (the 11 include variants, one host-side and one blocked case). In the default-rules run, auditd recorded specific telemetry for every successful payload.
  • E4: 1/7 → 4/7; process renaming (exec -a) and code via stdin still evaded both rule sets.
  • E2: 2 FP sources (my Python inline rule; default "Drop and execute new binary" on builds).
  • E5: overhead not distinguishable from baseline at n=5.

05 Takeaways

  • Blocked ≠ missed: check exit codes and audit records before blaming the detector.
  • Rule ordering matters: a default rule can shadow a custom one and turn a detection into a misattribution.
  • Rules matching on process name or argv are easy to evade; every new rule needs a benign-workload FP test.
  • Accountability survived privilege elevation: auditd logged auid=minh uid=root for sudo actions.

06 Limits

  • Small samples and a single VM.
  • I wrote both the variants and the rules, so the "unseen" test is not blind.
  • Overhead result is inconclusive, not "zero overhead".

AI security research plan

Planned, not done. Each lab has its research question and success criteria written before any testing, so the results cannot be framed after the fact.

Why this matters to clients

Organisations are deploying LLM assistants and agents faster than they can show that the guardrails work. These labs are designed to produce the kind of evidence the Measure function of the NIST AI RMF 1.0 (2023) asks for: a defined test, a metric, a result and its limits. That is the same discipline as the Falco lab, applied to AI systems.

  1. 01 Prompt-injection harness for a local LLM app

    planned
    Question
    Which classes of direct injection get past a defense that relies only on the system prompt, and how consistently?
    Setup
    Local model served in an isolated Docker network; model version, temperature and seed recorded; a small target app with a secret in its system prompt.
    Metric
    Attack success rate per payload class over N repetitions, against a success criterion fixed in advance; benign prompts to measure filter false positives.
    Maps to
    OWASP LLM01 Prompt Injection, LLM07 System Prompt Leakage · ATLAS AML.T0051

  2. 02 Indirect injection through a RAG pipeline

    planned
    Question
    How often does a poisoned document get retrieved, and once retrieved, how often does the model follow it? Do delimiting and provenance tags lower either rate?
    Setup
    Local RAG stack with a fixed corpus plus a small set of poisoned documents; the same queries run with and without each mitigation.
    Metric
    Retrieval rate × execution rate, reported separately so the weaker stage is visible.
    Maps to
    OWASP LLM01, LLM08 Vector & Embedding Weaknesses · ATLAS AML.T0051.001

  3. 03 Agent tool abuse vs. runtime detection

    planned
    Question
    When injected text makes an agent misuse its shell or file tools, can Falco/auditd plus tool-call logs detect it, and at what false-positive cost on normal agent tasks?
    Setup
    Local agent with sandboxed tools in a container with no egress; injection delivered through a document the agent reads; detection rules written and frozen before the attack variants.
    Metric
    Detection and attribution per case (direct / misattributed / missed / blocked), FP on benign agent tasks. The same method as the Falco lab.
    Maps to
    OWASP LLM06 Excessive Agency · tests the hypothesis in the Falco lab
