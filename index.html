Course research lab (IAM302) · Completed

Falco + auditd: Fileless Execution Detection in Docker

I tested how well Falco default rules, my custom rules and auditd detect and attribute fileless execution inside Docker containers, and measured the cost in false positives and overhead.

  • Ubuntu 22.04
  • Docker
  • Falco 0.45 modern eBPF
  • auditd
  • Bash
  • Python

E1 · Detection

4 → 8 of 11

Direct detections, default → custom rules (5 runs each). One case was blocked by Docker's noexec /dev/shm, not missed.

E4 · Unseen variants

1 → 4 of 7

Variants written after the rules were frozen. Strict fileless subset: 0 → 2 of 5. Small sample.

E2 · False positives

2 FP sources

My inline-code rule fired on benign python3 -c; gcc/make builds triggered a default rule.

E5 · Overhead

n=5 inconclusive

Differences stayed inside baseline variation, so no overhead figure is claimed.

IAM-relevant observations from this lab

  • Accountability across privilege elevation: auditd logged a sudo command as auid=minh uid=root, so the root action stayed traceable to the logged-in user. Falco alerts also carry user, uid and loginuid.
  • Least privilege in practice: parsing and analysis ran as an unprivileged user; audit logs were read through adm group membership; the Falco event file stayed root-only (0600); privileged steps were run explicitly with sudo.

This is a detection lab, not a dedicated IAM lab.

Read Case Study View Repository
Case study: Objective → Configuration → Test cases → Results → Takeaway

1 Objective

Fileless techniques (memfd, /dev/shm, /proc/self/fd, interpreter inline code, curl | bash, LD_PRELOAD, ptrace) run code without a normal on-disk binary. Which ones do runtime tools see, and does the alert name the right technique?

2 Tools / configuration

  • Ubuntu 22.04 VM, Docker containers on an internal network (Internet egress blocked and tested), benign payloads only.
  • Falco 0.45.0 modern eBPF: 25 default rules, then 6 custom rules; rule updates frozen and config hashes recorded per run.
  • auditd rules on memfd_create, execve/execveat and ptrace.
  • Bash test harness; Python parsers for Falco JSON and audit logs.

3 Test cases

  • 11 cases × 5 repetitions, each labelled direct, misattributed, missed or blocked.
  • 7 unseen variants written after the custom rules were frozen.
  • Benign workloads for false positives: container lifecycle, HTTP, container churn, PostgreSQL, gcc/make builds, Python.
  • Overhead vs. a no-monitoring baseline.

4 Results

  • E1: direct detection on 4/11 cases with default rules and 8/11 with custom rules (the 11 include variants, one host-side case and one blocked case). In the default-rules run, auditd recorded specific telemetry for every successful payload.
  • E4: 1/7 → 4/7 unseen variants; renaming the process (exec -a) or feeding code via stdin still evaded both rule sets.
  • E2: 2 false-positive sources (my Python inline rule; default "Drop and execute new binary" on builds).
  • E5: overhead not distinguishable from baseline at n=5.

5 Security takeaway

  • Blocked ≠ missed: check exit codes and audit results before blaming the detector.
  • Rule ordering matters: a default rule can shadow a custom one and turn a detection into a misattribution.
  • Rules that match on process name or argv are easy to evade; every new rule also needs a benign-workload FP test.
  • Limits: small samples, one VM, and I wrote both the variants and the rules, so the unseen test is not blind.
