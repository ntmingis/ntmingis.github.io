Case study: Problem → Approach → Tools → Evidence → Limitations → Lessons

1 Problem

Fileless techniques (memfd, /dev/shm, /proc/self/fd, interpreter inline code, curl | bash, LD_PRELOAD, ptrace) run code without a normal on-disk binary. I wanted to know which ones runtime security tools see, and whether alerts point to the right technique.

2 Approach

  • Isolated Docker lab on an internal network, benign payloads only.
  • 11 test cases × 5 repetitions, each classified as direct, misattrib, miss or blocked.
  • Default vs custom Falco rules; Auditd as a second telemetry source.
  • False-positive runs on benign workloads (container lifecycle, HTTP, container churn, builds, Python).
  • Held-out variants written after the custom rules were frozen.
  • Overhead measured against a no-monitoring baseline.

3 Tools

Ubuntu, Linux kernel, Docker, Falco (modern eBPF), Auditd. Bash automation for the test campaigns; Python parsers for Falco event JSON and audit logs, syscall analysis and log correlation.

4 Evidence

  • E1: custom rules reached direct detection on 8/11 cases (denominator includes variants and one blocked case).
  • E4: 4/7 on the original held-out set; 2/5 on the strict fileless subset.
  • E2: the custom Python inline rule produced FPs on benign workloads; gcc/make builds triggered the default "Drop and execute new binary in container" rule.
  • E5: runtime overhead not distinguishable from baseline variation at n=5.

5 Limitations

  • Small samples (n=5 per cell); single VM and runtime version.
  • Variants and rules were written by the same person, so the held-out test is not blind.
  • Results describe this lab setup, not production environments.

6 Lessons learned

  • Blocked ≠ miss: check exit codes and audit results before blaming the detector.
  • Rule ordering matters: a default rule can shadow a custom rule and turn a detection into a misattribution.
  • Every new rule needs a benign-workload FP test.
  • Measure before claiming overhead, and say so when the data cannot tell.
  • Validate the pipeline itself: clock skew, locale and log rotation all corrupted data at some point.
